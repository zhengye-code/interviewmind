# M7-3：把知识库接进评分

> **本步目标**：让评分时的 AI 能"查资料"，而不是只凭出题时自己编的参考要点。
>
> 关键结论提前说：**RAG 的价值不在通用知识，而在模型不知道的私有知识。**
> 本文最后一节有实测数据。

---

# 第 1 部分：接在哪

```
M6-2 的评分流程：
  读会话 → 读题目和回答 → 拼提示词 → 一次问 AI → 落库

M7-3 只改一步：
  读会话 → 读题目和回答 → 【每题检索知识库，材料拼进该题的材料块】 → 一次问 AI → 落库
```

**没有用 Advisor**，就写在 `InterviewGradingService.toFormattedString()` 里。理由：

| | Advisor | 写在拼提示词的地方 |
|---|---|---|
| 粒度 | 一次 AI 调用 | **可以精确到每一道题** |
| 10 道题各搜各的 | 做不到（一次调用只能注入一次） | ✅ 天然支持 |
| 检索结果拿得到吗 | 拿不到（有去无回） | ✅ 可以打日志、可以写进报告 |
| query 可控吗 | 只能用整个 user 消息 | ✅ 每道题用自己的检索词 |

> 结论：**评分是"N 道题一次调用"，而 Advisor 是"一次调用一次注入"** —— 粒度对不上，所以不用它。

---

# 第 2 部分：检索词选什么（这是本步最值钱的发现）

## 三个候选

| 候选 | 例子 | 直觉 |
|---|---|---|
| 题目文字 | "线上有一个下单接口……大促时 QPS 从 200 涨到 2000……怎么定参" | 最贴近用户问题 |
| **参考要点** | "能说明线程池核心参数在突发流量下的实际行为……能给出参数估算依据……" | 是"知识点陈述" |
| 题目 + 分类 | "……" + "JAVA" | 混搭 |

## 实测（同一道题，同一批知识块，阈值 0.6）

| 检索词 | 最高相似度 | 命中数 |
|---|---|---|
| **参考要点拼接** | **0.727 / 0.671 / 0.628** | **3 段全过阈值** ✅ |
| 完整题目文字 | 0.555 | 0 ❌ |
| 题目首句（62 字） | 0.525 | 0 ❌ |

## 为什么

**题目是"场景叙述"，知识库是"概念陈述"，两者语言风格不同，向量天然偏得远。**

```
题目：   线上有个下单接口，QPS 从 200 涨到 2000，任务排队严重，怎么定参
知识块： 联合索引让 WHERE 和 ORDER BY 同时用上索引，避免 filesort
         ↑ 这是"讲道理"的语言

参考要点：能说明线程池核心参数在突发流量下的实际行为……
         ↑ 这也是"讲道理"的语言 → 和知识块同构 → 相似度高
```

**RAG 的检索词要"长得像文档"，而不是"长得像问题"。**

> 这条规律在别的场景也一样：如果你的知识库是 API 文档，检索词用"函数签名 + 参数名"比用"我想实现什么功能"更准。

# 第 3 部分：阈值怎么定

## 实测数据（bge-m3 + 余弦相似度）

| 查询 | 内容 | 最高分 |
|---|---|---|
| "联合索引最左前缀" | 有对应块 | **0.730** |
| "索引失效的场景" | 有对应块 | **0.747** |
| "HashMap 扩容" | 有对应块 | **0.679** |
| "回表是什么" | 部分相关 | 0.540 |
| "深分页怎么优化" | 知识库没讲 | 0.510 |
| "线程池核心线程数怎么定"（旧知识库） | 没讲 | 0.525 |
| 完整题目文字 | 语言风格不匹配 | 0.50–0.56 |

## 结论

```
0.68 以上  →  真的相关
0.50–0.60  →  弱相关 / 噪声区
0.50 以下  →  基本无关
```

**阈值 0.6 正好卡在"真有对应内容"和"没有对应内容"的分界线上。** 这是一个经过实测校准的值，不是拍脑袋。

### 调阈值的方向

| 症状 | 怎么调 |
|---|---|
| 该检索到的没检索到 | 调低到 0.5，或者改检索词（见上） |
| 不相关的内容混进提示词 | 调高到 0.65–0.7 |
| 完全不准 | 先看切分：块是不是把多个主题混在一起了 |

# 第 4 部分：代码

## 4.1 常量

```java
private static final int RAG_TOP_K = 3;
private static final double RAG_SIMILARITY_THRESHOLD = 0.6;
/** 必须和 Chunker 写入 metadata 时的 key 一致 */
private static final String META_CATEGORY = "kbCategory";
```

**`META_CATEGORY` 提成常量**是关键 —— 写入端（Chunker）和读取端（这里）用同一个名字，才不会出现"key 写错导致永远检索不到"。

## 4.2 检索方法（带降级）

```java
private List<String> searchReferences(EvaluationItem item) {
    String query = buildQuery(item);
    if (query.isBlank()) {
        return List.of();
    }
    try {
        SearchRequest searchRequest = SearchRequest.builder()
                .query(query)
                .topK(RAG_TOP_K)
                .similarityThreshold(RAG_SIMILARITY_THRESHOLD)
                .filterExpression(new FilterExpressionBuilder()
                        .eq(META_CATEGORY, item.categoryKey())
                        .build())
                .build();

        List<Document> documents = vectorStore.similaritySearch(searchRequest);
        if (documents == null || documents.isEmpty()) {
            return List.of();
        }
        List<String> texts = new ArrayList<>(documents.size());
        for (Document document : documents) {
            if (document.getText() != null && !document.getText().isBlank()) {
                texts.add(document.getText());
            }
        }
        return texts;

    } catch (Exception e) {
        // 检索挂了不能把评分搞挂 —— 当"没检索到"继续
        log.warn("知识库检索失败，本题跳过 RAG 增强: questionIndex={}", item.questionIndex(), e);
        return List.of();
    }
}
```

**为什么必须有 try/catch**：`similaritySearch` 会调 embedding 接口。它一超时，整个评分就 500 —— 而评分本身要跑 30-60 秒，失败一次很贵。

## 4.3 检索词

```java
private String buildQuery(EvaluationItem item) {
    if (item.expectedPoints() != null && !item.expectedPoints().isEmpty()) {
        return String.join("；", item.expectedPoints());
    }
    return item.questionText() == null ? "" : item.questionText().trim();
}
```

## 4.4 拼进提示词

```
--- 第 1 题 ---
分类：MYSQL
题目：……
回答：……
参考要点：……
要点相关文档：
  文档1：……
  文档2：……
```

**材料放在"题目和要点"之后、"回答"之前**，让模型读完材料马上看到要评判的内容。

**多段之间必须换行**（`String.join("\n", ...)`），否则会拼成 "文档1：xxx文档2：yyy"。

## 4.5 提示词里必须有的三条规则

```
8. 判断命中时，优先参考「要点相关文档」——它来自知识库，比出题时生成的参考要点更权威；
9. 如果「要点相关文档」与「参考要点」冲突，以文档为准，并在 comment 里指出这一点；
10. 如果「要点相关文档」与题目明显无关（可能是检索错误），忽略它，只按参考要点判断。
```

**第 10 条别省**：检索一定会有错的时候，不给"忽略权"，模型会硬套无关材料。

# 第 5 部分：A/B 实验 —— 证明 RAG 到底有没有用

## 实验设计

```
同一个会话（3 道题、同样的回答）
  第一次：知识库里没有关于"线程池"的内容 → 检索 0 段
  第二次：加入一篇私有知识《公司订单服务线程池规范》 → 检索到 3 段
  其他一切不变，只换知识库
```

## 结果

| | 无 RAG | 有私有知识 |
|---|---|---|
| 第 0 题（线程池） | **5/10** | **4/10** |
| 评语 | "core=32 远不足以支撑 2000 QPS" | "选用 CallerRunsPolicy **直接违反文档3的硬性禁止项**" |
| 遗漏点 | 7 条（通用技术点） | 9 条，其中 4 条**引用文档编号** |

带 RAG 时的遗漏点原文：

```
- 核心线程数不低于目标并发的 1.5 倍（文档1）
- 队列未满之前不会创建超过核心线程数的线程（文档1）
- CallerRunsPolicy 与文档3「禁止使用……会拖死 Web 线程池」直接冲突
- 风控和发券必须使用隔离的线程池（文档3）
- 未提动态调整参数、保留旧配置、五分钟内回退（文档2）
```

**这就是 RAG 的价值**：模型本来就知道线程池原理，但它**不可能知道"你们公司禁止 CallerRunsPolicy"**。知识库给了它这个信息，它就能据此扣分。

## 反例：为什么通用知识看不出效果

第一轮实验用的知识库是 HashMap / B+ 树 / 缓存三大问题 —— 这些模型**本来就很熟**。

结果：检索命中了、材料进了提示词，但**分数几乎没变**（60 → 57，在 LLM 波动范围内 ±1）。

> **结论：如果模型已经会，知识库就是"补习"，增益很小。**
> **只有模型不知道的东西，RAG 才有增量。**

## 怎么判断你的知识库值不值得建

问自己一句：

> **这段内容，直接问 ChatGPT 它能答对吗？**

- 能答对（HashMap 原理、B+ 树）→ 建了增益小，主要价值是"统一口径"
- 答不对（公司规范、内部架构、私有中间件、业务术语）→ **这才是 RAG 的主场**

# 第 6 部分：验收清单

```
1. POST /api/knowledge/reindex
     期望 imported=文档数, failed=0
2. GET /api/knowledge/search?q=<参考要点>&category=<分类>
     期望 score > 0.6，返回的 title 和题目相关
3. 若返回 0 段：
     a) 把 threshold 调低到 0.4 再看真实分数
     b) 换检索词（用参考要点，别用题目）
     c) 检查 metadata 的 kbCategory 是否等于分类名（大写）
4. 跑一次评分，看返回的 missedPoints 里有没有引用文档内容
```

**第 3 步永远是排障起点**：检索不准的时候接进评分，只会让评分更差。

# 第 7 部分：踩过的坑（按重要性）

| 坑 | 现象 | 原因 |
|---|---|---|
| **metadata key 不一致** | 检索永远 0 条，且不报错 | 写入用 `kbCategory`，读取用 `category` |
| **分类大小写不一致** | 同上 | 目录名是 `redis`，配额里是 `REDIS` |
| **检索词用题目** | 命中有内容也搜不到 | 语言风格不匹配，相似度天然低 0.2 |
| **阈值太高** | 全部被过滤 | 0.6 是短查询的分界线，长文本要降到 0.5 |
| **检索没 try/catch** | embedding 超时 → 整个评分 500 | 外部依赖必须降级 |
| **多段材料不换行** | 模型分不清哪段是哪段 | `String.join("")` |
| **提示词没写使用规则** | 材料进去了但模型不用 | 必须明确"优先参考""冲突以文档为准""无关可忽略" |

# 第 8 部分：这一步之后

```
✅ 知识库能导入（4 篇 → 16 个块）
✅ 能按语义检索、按分类过滤、阈值可控
✅ 评分时逐题检索，材料拼进对应题目下
✅ 已验证：私有知识能改变评分与评语
```

**下一步可以做（按价值排序）**：

| 方向 | 说明 |
|---|---|
| **补私有知识** | 让知识库覆盖"模型答不对"的内容，这才是 RAG 的战场 |
| **检索再加一层过滤** | 按 `isPart`、按小节标题，避免把长块的碎片塞进去 |
| **把检索结果写进报告** | 报告里标注"本题依据《XX规范》第 2 节"，可追溯性大幅提升 |
| **重排序（rerank）** | 向量召回 topK=10，再用一个模型挑出最相关的 2 段 |
| **Workflow（M8）** | 把"检索 → 分析 → 打分 → 汇总"串成可观测、可重试的流水线 |
