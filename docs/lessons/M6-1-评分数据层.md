# 第 1 部分：要建哪两张表

## 1.1 为什么是两张，不是一张

评分结果有两种"粒度"：

| 粒度 | 一次面试有几条 | 内容举例 |
|---|---|---|
| **逐题分** | 10 条 | 第 3 题：7 分，命中 2 条要点，漏了"回滚方案" |
| **整场报告** | 1 条 | 总分 68，总结"基础扎实但缺乏深度"，建议 3 条 |

**一张表装不下两种粒度**：

```
如果塞一张表：
  id | session_id | question_id | score | summary | ...
   1 |     7      |     101     |   7   |  NULL   |   ← 逐题行，summary 空着
   2 |     7      |    NULL     | NULL  | 总结…   |   ← 报告行，一堆空字段
```

结果是**一半的列永远是 NULL**，而且没法加"一场只能有一条报告"这种约束（因为逐题行也在这张表里）。

> 判断标准：**"数量不一样"的东西，就该放不同表。**
> 10 条 vs 1 条 —— 不是同一类东西。

## 1.2 表 1：`interview_question_scores`（逐题分）

| 列 | 类型 | 含义 |
|---|---|---|
| `id` | BIGINT 自增 | 主键 |
| `session_id` | BIGINT | 哪场面试 |
| `question_id` | BIGINT | 哪道题 |
| `score` | INTEGER | 这一题得几分（0–10） |
| `hit_points_json` | TEXT | 回答命中了哪几条参考要点（JSON 数组） |
| `missed_points_json` | TEXT | 漏了哪几条（JSON 数组） |
| `comment` | TEXT | 一句评语 |
| `created_at` | TIMESTAMP | 评分时间 |

### 为什么存 `session_id`，它不是能从 `question_id` 查出来吗

没错，`session_id` 是**冗余**的：拿到 `question_id`，去 `interview_questions` 表一查就知道属于哪场面试。

**那为什么还要存？** 因为最常见的查询是：

```
"把第 7 场面试的所有评分查出来"
```

- 不存 `session_id`：要先查题目表找到属于第 7 场的 10 个 question_id，再用 `IN (...)` 去评分表查 —— 两次查询 + 一个列表
- 存了 `session_id`：一条 `WHERE session_id = 7` 就搞定，走索引

**这叫"有意的冗余"**：用一点点存储空间（8 字节）换掉一次 join。

这和 M4-2 里把配额存成 `plan_json` 是同一个思路 —— **能推导出来的东西，如果查询频繁且推导昂贵，就冗余存一份**。

⚠️ 代价：两个地方要同时维护。这就是为什么 `session_id` 必须由代码保证和题目一致（M6-2 里会看到）。

### 为什么 `question_id` 加唯一约束

```sql
CONSTRAINT uk_iqs_question UNIQUE (question_id)
```

**一道题只能有一条评分记录。**

为什么需要这个约束？因为评分服务可能会被重复调用（用户连点、前端重试）。有了唯一约束：

```
第 1 次评分：写入成功
第 2 次评分：写入被数据库拒绝
```

即使代码里的幂等判断失效了，**数据库也不会让你存出两份矛盾的评分**。

> 这叫"用数据库兜底"。代码的检查是"尽量不出错"，数据库的约束是"错了也进不来"。

⚠️ **这条约束也决定了将来的扩展方式**：如果哪天要"保留每次重评的历史"，就必须**删掉这条唯一约束**，改成"按时间取最新一条"。

**约束本身就是一份设计决定，写下来就等于记下了当时的取舍。**

### 为什么 `score` 是 0–10 的整数，不是 0–100

三个理由：

1. **更诚实**：让 AI 给"87 分"和"88 分"没有区别，那是假精确。0–10 的粒度足够区分"很差/一般/不错/很好"。
2. **更好写提示词**：告诉模型"给 0 到 10 的整数"，比"0 到 100"更容易守规矩。
3. **前端好画**：10 分制直接就是"10 个格子填几个"。

**注意 `NOT NULL`**：没评出分就不该有这一行，而不是存一个 `NULL` 分数。`NULL` 会让后面所有计算都要判空。

## 1.3 表 2：`interview_reports`（整场报告）

| 列 | 类型 | 含义 |
|---|---|---|
| `id` | BIGINT 自增 | 主键 |
| `session_id` | BIGINT | 哪场面试（**唯一**） |
| `overall_score` | INTEGER | 总分（0–100） |
| `summary` | TEXT | 总体评价 |
| `strengths_json` | TEXT | 优势（JSON 数组） |
| `suggestions_json` | TEXT | 改进建议（JSON 数组） |
| `model` | VARCHAR(100) | 用哪个模型评的 |
| `evaluated_at` | TIMESTAMP | 评分时间 |

### 为什么 `session_id` 唯一

```sql
CONSTRAINT uk_ir_session UNIQUE (session_id)
```

**一场面试只能有一份报告。**

这条约束顺便当了"幂等开关"：想判断"这场面试评过没有"，直接 `SELECT ... WHERE session_id = ?`，查到就是评过了。不需要额外的状态列。

### 为什么留 `model` 这一列

将来可能会换模型（更便宜的、更强的、或者加了 RAG 的版本）。

存下来之后你能回答：

```
"为什么第 3 场面试的总分这么低？"
→ 哦，那场是用 deepseek-chat 评的，后面换了模型
```

**没有这一列，历史数据就永远说不清是怎么产生的。** 这在 AI 应用里特别重要，因为同一个提示词换个模型，结果可能差很多。

### ⚠️ 一个重要决定：总分由代码算，不由 AI 给

这一步我在上次讨论时说过"报告建议三个维度分"，现在**改成不做了**。原因是：

如果逐题分是 AI 给的（0–10），总分也是 AI 给的（0–100），那就可能出现：

```
10 道题：6, 7, 5, 8, 6, 5, 7, 6, 4, 6      平均 6.0
报告里的总分：72                              ← 平均×10 应该是 60
```

**两个数字对不上，而且你没法判断哪个是错的。**

所以定一条规矩：

| 谁负责 | 做什么 |
|---|---|
| **AI** | 给每题打分、写评语、写总结、写优势、写建议（**文字和判断**） |
| **代码** | 算总分（`平均分 × 10`，四舍五入）、算及格题数、算各分类平均（**数值计算**） |

**数值计算交给代码，文字判断交给 AI。** 这条分工在 AI 应用里非常实用，因为模型算数不可靠（尤其多步计算），但它写评语是你的代码写不出来的。

> 将来如果想要"正确性 / 深度 / 表达"三个维度分：加三列，让 AI 给（那是**判断**，不是**计算**）。加列在 Postgres 里是一条 `ALTER TABLE`，不用重做表。

## 2.1 迁移脚本

`src/main/resources/db/migration/V6__add_interview_evaluation.sql`

```sql
-- V6: 面试评分结果（M6）

-- ① 逐题评分：一道题一行
CREATE TABLE interview_question_scores (
    id                  BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    session_id          BIGINT       NOT NULL,
    question_id         BIGINT       NOT NULL,
    score               INTEGER      NOT NULL,
    hit_points_json     TEXT,
    missed_points_json  TEXT,
    comment             TEXT,
    created_at          TIMESTAMP(6) NOT NULL,
    CONSTRAINT fk_iqs_session
        FOREIGN KEY (session_id) REFERENCES interview_sessions(id) ON DELETE CASCADE,
    CONSTRAINT fk_iqs_question
        FOREIGN KEY (question_id) REFERENCES interview_questions(id) ON DELETE CASCADE,
    CONSTRAINT uk_iqs_question UNIQUE (question_id),
    CONSTRAINT ck_iqs_score CHECK (score BETWEEN 0 AND 10)
);

CREATE INDEX idx_iqs_session ON interview_question_scores(session_id);

-- ② 整场报告：一场面试一行
CREATE TABLE interview_reports (
    id                  BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    session_id          BIGINT       NOT NULL,
    overall_score       INTEGER      NOT NULL,
    summary             TEXT,
    strengths_json      TEXT,
    suggestions_json    TEXT,
    model               VARCHAR(100),
    evaluated_at        TIMESTAMP(6) NOT NULL,
    CONSTRAINT fk_ir_session
        FOREIGN KEY (session_id) REFERENCES interview_sessions(id) ON DELETE CASCADE,
    CONSTRAINT uk_ir_session UNIQUE (session_id),
    CONSTRAINT ck_ir_score CHECK (overall_score BETWEEN 0 AND 100)
);

CREATE INDEX idx_ir_evaluated ON interview_reports(evaluated_at DESC);
```

### 逐条解释

**`ON DELETE CASCADE`**：会话被删时，它的评分也一起删。

对比 M4-2 里 `interview_sessions.resume_id` 用的是 `ON DELETE SET NULL`（简历删了，面试记录要留着）。这里的区别是：

| 关系 | 删父记录时 | 理由 |
|---|---|---|
| 简历 → 面试会话 | `SET NULL` | 面试是**历史成绩**，简历没了也要留下 |
| 会话 → 题目 / 评分 / 报告 | `CASCADE` | 这三样**离开了会话就没有意义** |

**判断标准：这东西能不能"独立存在"？** 能 → `SET NULL`；不能 → `CASCADE`。

**`ck_iqs_score CHECK (score BETWEEN 0 AND 10)`**：数据库层面的校验。

为什么代码里已经会限制 0–10，还要在数据库再写一遍？

```
提示词约束   → 让 AI 尽量给 0-10
代码校验     → 拦下不合规的值，报错或修正
数据库 CHECK → 万一前两层都漏了，依然进不来
```

三层都要有，因为每层都可能失效：AI 不听话、代码有 bug、有人直接连数据库改数据。

> 这是"**纵深防御**"：不假设任何一层永远不会出错。

**两个索引**：
- `idx_iqs_session`：按场次查评分（用得最多）
- `idx_ir_evaluated`：按评分时间倒序查（做"最近评过的面试"列表时会用）

**`idx_iqs_question` 不用建** —— 因为 `uk_iqs_question` 这个唯一约束会自动创建一个索引，按 `question_id` 查已经很快了。**唯一约束 = 索引 + 不能重复**。

## 2.2 实体 1：`InterviewQuestionScoreEntity`

`src/main/java/com/interviewmind/modules/interview/model/InterviewQuestionScoreEntity.java`

```java
package com.interviewmind.modules.interview.model;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.PrePersist;
import jakarta.persistence.Table;
import lombok.Getter;
import lombok.Setter;
import org.hibernate.annotations.Check;

import java.time.LocalDateTime;

/** 一道题的评分结果 */
@Getter
@Setter
@Entity
@Table(name = "interview_question_scores")
@Check(constraints = "score >= 0 AND score <= 10")
public class InterviewQuestionScoreEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    /** 冗余字段：方便"查一场面试的全部评分"，不用先查题目表 */
    @Column(name = "session_id", nullable = false)
    private Long sessionId;

    /** 一道题只能有一条评分 */
    @Column(name = "question_id", nullable = false, unique = true)
    private Long questionId;

    /** 0-10 分 */
    @Column(name = "score", nullable = false)
    private Integer score;

    /** 命中的参考要点（JSON 数组字符串） */
    @Column(name = "hit_points_json", columnDefinition = "TEXT")
    private String hitPointsJson;

    /** 遗漏的参考要点（JSON 数组字符串） */
    @Column(name = "missed_points_json", columnDefinition = "TEXT")
    private String missedPointsJson;

    @Column(name = "comment", columnDefinition = "TEXT")
    private String comment;

    @Column(name = "created_at", nullable = false)
    private LocalDateTime createdAt;

    @PrePersist
    protected void onCreate() {
        if (createdAt == null) {
            createdAt = LocalDateTime.now();
        }
    }
}
```

### `@Check` 是干什么的，为什么 Flyway 里也写了一遍

`@Check` 是 Hibernate 的注解，作用只有一个：**Hibernate 自己建表时，把这条约束也加上**。

那什么时候 Hibernate 会自己建表？**跑单元测试的时候**（测试用 H2 内存库，`ddl-auto=create-drop`）。

所以现在的分工是：

```
生产/开发环境：Flyway 执行 V6 建表，CHECK 来自 SQL 文件
单元测试环境：Hibernate 根据实体建表，CHECK 来自 @Check 注解
```

**两处写同一件事，是有意的**：因为两个环境用两个不同的建表工具。如果你只在 SQL 里写，测试环境的 H2 就没有这条约束，测试通过但生产报错 —— 那才是真的坑。

> 这个"重复"值得记：**凡是"两套建表工具"并存的项目，都逃不掉这种同步维护。** 看到它别奇怪，但要记得改一处就得改另一处。

### `unique = true` 和 SQL 里的 `UNIQUE` 也是同样的关系

`@Column(unique = true)` → 测试环境 H2 会建唯一索引
`CONSTRAINT uk_iqs_question UNIQUE (...)` → 开发/生产环境由 Flyway 建

import jakarta.persistence.Entity;

## 2.4 仓库 1：`InterviewQuestionScoreRepository`

`src/main/java/com/interviewmind/modules/interview/repository/InterviewQuestionScoreRepository.java`

```java
package com.interviewmind.modules.interview.repository;

import com.interviewmind.modules.interview.model.InterviewQuestionScoreEntity;
import org.springframework.data.jpa.repository.JpaRepository;

import java.util.List;
import java.util.Optional;

public interface InterviewQuestionScoreRepository
        extends JpaRepository<InterviewQuestionScoreEntity, Long> {

    /** 一场面试的全部逐题评分 */
    List<InterviewQuestionScoreEntity> findBySessionId(Long sessionId);

    /** 某一道题的评分 */
    Optional<InterviewQuestionScoreEntity> findByQuestionId(Long questionId);

    /** 这一场评了几道题 */
    long countBySessionId(Long sessionId);
}
```

**为什么没有 `existsBySessionId`**：判断"这场评过没有"应该看 `interview_reports`，不是看逐题分。逐题分可能只写了一部分（比如中途失败），`interview_reports` 才是"评分流程完整跑完"的标志。

> **找一条记录来代表"这件事做完了"，比"数一数子记录有几个"可靠。** 这就是报告表存在的额外意义。

## 2.5 仓库 2：`InterviewReportRepository`

`src/main/java/com/interviewmind/modules/interview/repository/InterviewReportRepository.java`

```java
package com.interviewmind.modules.interview.repository;

import com.interviewmind.modules.interview.model.InterviewReportEntity;
import org.springframework.data.jpa.repository.JpaRepository;

import java.util.Optional;

public interface InterviewReportRepository
        extends JpaRepository<InterviewReportEntity, Long> {

    /** 一场面试的报告；也是"评过没有"的判断依据 */
    Optional<InterviewReportEntity> findBySessionId(Long sessionId);

    boolean existsBySessionId(Long sessionId);
}
```

### 顺带说说这些方法名是怎么来的

Spring Data 不需要你写 SQL，它**从方法名猜查询**：

| 方法名 | 生成的 SQL 大意 |
|---|---|
| `findBySessionId` | `SELECT * WHERE session_id = ?` |
| `findByQuestionId` | `SELECT * WHERE question_id = ?` |
| `countBySessionId` | `SELECT count(*) WHERE session_id = ?` |
| `existsBySessionId` | `SELECT exists(...) WHERE session_id = ?` |

规则就三条：

```
① findBy / countBy / existsBy  →  决定"做什么"
② 中间的 SessionId            →  实体字段名（首字母大写）
③ and / Or / OrderBy / Asc    →  可以串联
```

**字段名拼错会怎样？** 启动时直接失败，报 `No property 'sesssionId' found`。这是好事 —— **启动就炸，比运行时才炸好**。

# 第 4 部分：常见错误

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 启动报 `missing table [interview_reports]` | V6 没执行 | 文件名必须是 `V6__add_interview_evaluation.sql`（两个下划线） |
| 启动报 `wrong column type ... found: int8, expected: int4` | SQL 里写了 `BIGINT`，实体是 `Integer` | 看 `overall_score` 和 `score` 这两列，必须 `INTEGER` |
| 启动报 `No property 'sessionId' found` | 仓库方法名和实体字段对不上 | 检查实体里字段是不是真叫 `sessionId` |
| H2 测试报找不到表 | `spring.flyway.enabled=false`，测试靠 Hibernate 建表 | 确认实体有 `@Entity` 和 `@Table(name=...)` |
| `@Check` 报找不到符号 | 少了 import | `import org.hibernate.annotations.Check;` |
| psql 插入报 `violates foreign key` | `session_id` / `question_id` 填了不存在的值 | 先查一下这两个 id 真的存在 |
| 想把 `score` 改成 0-100 | 要同时改 SQL、实体、`@Check`、提示词 | 三处必须一致，否则测试和生产行为不同 |
